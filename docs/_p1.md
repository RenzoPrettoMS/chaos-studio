## Executive Summary

The `startchaos` plugin **already ships a working end-to-end chaos journey**: five skills (`start-chaos`, `create-workspace`, `setup-scenario`, `run-scenario`, `chaos-impact`), a shared PowerShell library with resumable state, a mature Azure Monitor impact-report pipeline with its own JSON schema and an offline replay harness, and an MCP server exposing fifteen typed tools across workspace, scenario, run and Monitor surfaces — all released as v0.3.0 and tested in CI on three operating systems and four Python versions. **This plan is an evolution of that product, not a replacement for it.**

The evolution is driven by a field engagement in which the shipped surface — plus an unmerged prototype loop — produced two *unsound* verdicts and one lost investigation. The gaps were specific, not architectural: an Event Hubs fault was reported as landed while the data plane was demonstrably undisrupted; the same pre/during/post telemetry bundle was hand-assembled four times; "did an alert fire inside the window" had no first-class tool; App Insights queries failed three times on schema and subscription quirks; three MCP tools the prompt named were not visible in the session; run IDs and per-action identity had to be recovered by inference; and the working state was destroyed by a directory wipe. This plan turns each of those into a **narrow, backward-compatible improvement to a named existing file**, and only proposes new modules where an existing return contract cannot safely express the operation.

Concretely: `chaos-impact` and its schema, metric tables, KQL templates, Pester tests and offline replay are **extended, never replaced**; `create-workspace` is retained and extended with scope resolution and dry-run planning; `setup-scenario` is refactored around typed configuration, exclusions and real validation; `run-scenario` keeps its ScenarioRun-ID resolution but stops passing `--skip-validation` behind a compatibility window; `start-chaos` keeps its orchestration and state contract and gains resumable evidence; `monitor.py` grows alert-instance, App Insights and fault-window capability with `server.py` wrappers and additions to `tests/test_monitor_tools.py`. Eight **targeted capabilities** — scope-setup, inventory, availability, analyze, recommend, run, diagnose, evidence — are layered as additive skills that compose these existing assets, with consolidation where a shipped skill already owns that leg of the journey. All five existing skill names, all fifteen existing tool names, the `{"ok": …}` envelope, the `startchaos-state.json` state contract and `impactReportSchemaVersion: 1` continue to work unchanged; sequencing therefore begins with backward-compatible hardening of what already exists (Epic 0), and every later epic carries an acceptance criterion proving the shipped workflows still pass.

## Background

### (A) Current state — `copilot-cli-plugin` on `main` at the pinned SHA

**Plugin manifest.** `copilot-cli-plugin/plugin.json` declares `name: "startchaos"`, `version: "0.3.0"`, `skills: "skills/"`, `agents: "agents/"`, and one MCP server under `mcpServers`: key **`chaos-studio`**, `command: "chaos-mcp"`, with `install: {type: "python", path: "mcp/"}`. `.github/plugin/marketplace.json` declares the marketplace `chaos-studio` at version `0.3.0` and exposes exactly one plugin, **`startchaos`**, sourced from `./copilot-cli-plugin`. `copilot-cli-plugin/mcp/pyproject.toml` declares package `chaos-mcp` version **`0.3.0`**, `requires-python >=3.10`, dependencies `mcp>=1.2.0,<2` and `httpx>=0.27.0`, and the console script `chaos-mcp = chaos_mcp.server:main`.

**Five skills ship.** Each is a natural-language wrapper over a PowerShell entry script; the model's job is to set `$env:STARTCHAOS_STATE_PATH`, invoke the script, and translate exit codes into `ask_user` prompts. SKILL.md frontmatter today carries exactly two keys, `name` and `description`; there is no machine-readable trigger-phrase or tool-requirement declaration.

| Skill | Entry script | Exit codes | Role |
|---|---|---|---|
| `start-chaos` | `Invoke-StartChaos.ps1` | 0/1/2/3/4 | Orchestrating front door; four-phase pipeline with resume |
| `create-workspace` | `Invoke-CreateWorkspace.ps1` | 0/1 | Workspace + identity + Reader RBAC provisioning |
| `setup-scenario` | `Invoke-SetupScenario.ps1` | 0/1/2/3 | Recommendation refresh, configuration build, validate→fix→re-validate |
| `run-scenario` | `Invoke-RunScenario.ps1` | 0/1 | Execution (`az chaos scenario run start --skip-validation --no-wait`) and status streaming |
| `chaos-impact` | `Invoke-ChaosImpact.ps1` + 5 helpers | 0/1/2/3/4 | Post-run Azure Monitor impact report |

`agents/start-chaos.md` declares an orchestrator agent with `tools: [powershell, view, ask_user]`, the trigger phrases *"start chaos"*, *"run chaos experiment"*, *"chaos studio"*, *"create workspace"* in its description, the four-phase order, the resume protocol keyed on `auth/workspace/setup/run` status, and a closing hand-off suggestion to `/chaos-impact <scenarioRunId>`.

**Shared PowerShell library** (`copilot-cli-plugin/scripts/`): `Ensure-AzLogin.ps1` (`Ensure-AzLogin`), `Invoke-AzRest.ps1` (`Invoke-AzRest`), `Invoke-AzChaos.ps1` (`Initialize-ChaosExtension`, `Invoke-AzChaos` — auto-installs the `chaos` CLI extension), `Wait-AzureLro.ps1` (`Wait-AzureLro`), `Rbac.ps1` (`Test-CallerCanAssignRoles`, `Grant-Reader`, `Build-RoleAssignmentRemediation`), `State.ps1` (`Get-StatePath`, `New-EmptyState`, `Read-State`, `Save-State`, `Set-StateProperty`), `Render.ps1` (`Write-Card`, `Write-Table`, `Write-Error-Card`), `Validate-AndFix.ps1` (`Invoke-ValidateAndFix`), `New-RunReport.ps1` (`New-RunReport`).

**State is resumable but repo-local.** `Get-StatePath` returns `$env:STARTCHAOS_STATE_PATH` when set and otherwise falls back to `Join-Path $PWD 'startchaos-state.json'`. Writes are atomic (temp file then rename) and stamp `stateSchemaVersion: 1` and `updatedAt`. The v1 state document carries `context`, `auth`, `workspace`, `setup` (including `configuration.validation.permissionFix`) and `run` (including `scenarioRunId`, `lastObservedState`, `actions[]`, `errors[]`). **There is no durable evidence store outside the repository working tree today** — that is class C, and this plan must not be read as saying otherwise.

**`chaos-impact` is the most mature asset in the repository** and the strongest reuse candidate:

- `schema/impact-report.schema.json` (draft-07) with required top-level fields `impactReportSchemaVersion`, `generatedAt`, `scenarioRunId`, `workspace`, `scenario`, `window`, `actions`, `coverage`, `queries`, `errors`, and signal classes `chaosAttributed` / `baseline` / `unexplained` / `platformEvent`;
- `scripts/Constants.ps1` — the repository's most complete API-pin file, covering diagnostic settings `2021-05-01-preview`, metrics `2024-02-01`, Log Analytics `v1` at `https://api.loganalytics.io`, activity log `2015-04-01`, **AlertsManagement `2023-05-01-preview` with a `2018-05-05` fallback**, **Resource Health `2022-10-01`**, Chaos Studio `2026-05-01-preview`, Log Analytics workspace `2022-10-01`, plus tunables (`MaxResources` 50, `Buffer` PT5M, `DiagThrottleLimit` 4, `StateSchemaVersion` 1) and the `Get-ChaosImpactConstants` getter;
- `Get-MonitorSignals.ps1` — throttled parallel metric fan-out, KQL workspace grouping, activity-log filtering, **alerts and Resource Health parsing**, per-resource error isolation and coverage markers;
- `Build-ImpactCorrelation.ps1` — a pure-function correlation and classification engine with per-action window fallback and severity bucketing;
- `Get-DiagnosticSettings.ps1`, `New-ImpactReport.ps1`, three KQL templates, per-resource-type metric/threshold tables in `templates/metrics/defaults.json`, and `templates/report.md.tmpl`;
- four Pester unit suites (`Build-ImpactCorrelation`, `Get-MonitorSignals`, `Invoke-ChaosImpact`, `New-ImpactReport`);
- an **offline replay E2E** — `tests/e2e/Run-OfflineReplay.ps1` stages a temp tree, substitutes a fixture-serving stub for `Invoke-AzRest.ps1`, runs `Invoke-ChaosImpact.ps1` in a child `pwsh`, and `OfflineReplayE2E.Tests.ps1` asserts the rendered `impact-<runId>.json` against `expected-impact.json`, backed by seven `recorded-*.json` fixtures (`run`, `workspace-check`, `diag-settings`, `metrics`, `activity`, `alerts`, `health`).

**The MCP server.** `chaos_mcp` exposes **exactly 15 tools, and all 15 `@mcp.tool()` decorators are in `copilot-cli-plugin/mcp/chaos_mcp/server.py`.** `monitor.py` contains **helper implementations for the three monitor tools and no decorators at all** — it defines `monitor_query_metrics`, `monitor_query_logs`, `monitor_search_activity_log` plus `_validation_error` and `_envelope`, and `server.py` wraps each one in a decorated function. Any statement that the fifteen tools are "across `server.py` and `monitor.py`" is wrong and is corrected here.

All tools share the envelope `{"ok": true, "result": …}` / `{"ok": false, "errorType": …, "error": …, "statusCode": …, "details": …}`, with `errorType` `PermissionDenied` on 403, `AuthenticationFailed` on 401 and `AzureError` otherwise. `azure.py` carries the runtime auth-mode lever (`cli` vs `managed-identity`, precedence override → `CHAOS_MCP_AUTH_MODE` → default), IMDS and App Service identity endpoints, ARM helpers with retry on 429/500/502/503/504 honouring `Retry-After` with exponential backoff capped at 30 s, `wait_for_lro`, and the `_TEST_TRANSPORT` `httpx.MockTransport` hook that makes the whole surface unit-testable offline.

**API-version pins are distributed, not centralised.** At the pinned SHA they live in four places: `azure.py` (`DEFAULT_API_VERSION = "2026-05-01-preview"`, `IMDS_API_VERSION = "2018-02-01"`, `APP_SERVICE_IDENTITY_API_VERSION = "2019-08-01"`), `monitor.py` (`METRICS_API_VERSION = "2024-02-01"`, `ACTIVITY_LOG_API_VERSION = "2015-04-01"`), `server.py` (`ROLE_ASSIGNMENT_API_VERSION = "2022-04-01"`), and PowerShell `skills/chaos-impact/scripts/Constants.ps1` (nine pins, listed above; `Rbac.ps1` additionally carries `2022-04-01` inline). NFR-9 is therefore a *target state*, not a description.

**API-version verification.** `2026-05-01-preview` **does exist**: verified against `Azure/azure-rest-api-specs`, `specification/chaos/resource-manager/Microsoft.Chaos/Chaos/examples/`, which carries example folders for `2024-11-01-preview`, `2025-01-01` (stable/GA), `2026-05-01-preview` and `2026-08-01-preview`. It is not surfaced in the rendered Learn REST reference, which is why it can appear "not publicly indexed". The existing pin is valid; whether to *move* to `2026-08-01-preview` is Q6. Runtime availability of any given operation in a customer's tenant remains an open question (Q6), not a repository fact.

**CI and release.** `.github/workflows/test.yml` runs three jobs on push and PR to `main`: **Pester** ≥ 5.5.0 over `./copilot-cli-plugin/skills` on `ubuntu-latest`, `windows-latest` and `macos-latest` with NUnit results uploaded; **pytest** with `--cov=chaos_mcp` on Python **3.10, 3.11, 3.12, 3.13** after `pip install -e .` plus `pytest pytest-cov httpx` (note: `jsonschema` is *not* installed); and **ruff** (`ruff check chaos_mcp tests`) on Python 3.12. `.github/workflows/release.yml` triggers on `v*` tags and has three jobs: build sdist+wheel for `chaos-mcp`, publish to PyPI via a trusted-publisher OIDC flow to `https://pypi.org/p/chaos-mcp`, and create a GitHub Release with generated notes and the dist artifacts attached. **Whether `chaos-mcp` has actually been published to PyPI is not provable from the repository and is treated as an open question (Q13).**

**Other shipped assets.** `copilot-cli-plugin/README.md`, `CHANGELOG.md`, `CONTRIBUTING.md`, `docs/impact-synthesis-skill.md`, `mcp/README.md`, `mcp/LICENSE`, `mcp/mcp-config.example.json`, `.chaos-plugins.yaml.example`; repository-level `README.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, issue/PR templates, `CODEOWNERS`, `dependabot.yml`; `samples/README.md` and `samples/aks-zone-down-demo/**` (`AGENTS.md`, `README.md`, `deploy.sh`, `cleanup.sh`); `scenarios/README.md`.

### Why now

1. **Chaos Studio v2 (workspace) surfaces most of the data a prompt-side table would have to fake.** Workspace-scoped `POST …/discover` and `POST …/evaluate` with their `discoveries/latest` and `evaluations/latest` singletons; `Scenario.properties.recommendation.recommendationStatus`; `Scenario.properties.actions[].actionId` (URN, e.g. `urn:csci:microsoft:compute:shutdown/1.0.0`); and the Actions / Action Versions / Connections / Discovered Resources / Private Accesses operation groups mean scenario availability can be *read* rather than *guessed*. `main` already reaches part of this surface through T5 and T6.
   **Scoping correction:** `validations/latest` is **not** a workspace artifact. Verified against `scenarioConfiguration.models.tsp` in `Azure/azure-rest-api-specs`, `Validation` is `@parentResource(ScenarioConfiguration)` `@singleton("latest")`, so the real path is `.../workspaces/{ws}/scenarios/{s}/configurations/{c}/validations/latest`, reached by `POST .../configurations/{c}/validate` — exactly what T8 already calls. `fixResourcePermissions` (T9) is likewise configuration-scoped. **There is no way to obtain per-resource permission blockers without first creating a ScenarioConfiguration**; workspace `evaluate` carries only aggregate template-evaluation counts and a per-template `RecommendationStatus`. This drives the two-tier availability design (§Permission-Blocker Acquisition).
2. **`ScenarioConfiguration.properties.resourceTargeting`** gives a symmetric `include` / `exclude` primitive over `physicalZones` (`{region}-az{N}`), `zones`, `locations`, `resources` (ARM IDs), `tags` and `types` (trailing wildcard). Include is AND across dimensions; exclude is OR; exclude wins. It is a real, computable blast-radius primitive — and per F8 the only mechanism for starving a single dependency leg. T7 already accepts the configuration body as an opaque dict, so supporting it is additive.
3. **`az chaos setup` reached GA**, collapsing RG + workspace + identity + Reader + evaluate into one command (`--skip-permissions`, `--skip-evaluation-wait`), which makes a thin scope-setup extension of `create-workspace` viable rather than a new provisioning stack.

#### Corrections to the field record (external verification)

Field evidence is observational and was recorded under time pressure. Two *explanations* attached to it have since been falsified. The **observations** stand; the **mechanisms** do not, and the distinction matters because this plan turns mechanisms into normative documents.

| Item | Recorded explanation | Verification result | Consequence |
|---|---|---|---|
| **F4-c** | "`first` is a reserved token in KQL." | **Falsified.** `first` is not a KQL keyword or operator (KQL uses `take`/`limit`; `arg_min`/`arg_max` for first-row selection). `--first` is an Azure CLI / Resource Graph paging parameter mapping to REST `$top`, max 1000. The probable real cause is CLI argument parsing, not KQL syntax. | **No escaping layer is built.** The App Insights work implements only the two verified fixes. Re-deriving the third failure is **Q11**. |
| **F6** | "`AmqpSender` caches `MaxMessageSize` after first attach." | **Falsified.** In `Azure.Messaging.EventHubs`, `AmqpProducer.CreateLinkAndEnsureProducerStateAsync` sets `MaximumMessageSize` on **every** link open, with the source comment *"Update the known maximum message size each time a link is opened…"*. (`InitializedPartitionProperties` *is* cached once; `MaximumMessageSize` is not.) | The **observation** — namespace `Disabled` with 60/60 successful sends — is unaffected and remains the canonical case for two-sided attestation. The seed entry of `fault-semantics.md` states only what was observed, with the candidate mechanism marked `mechanismConfidence: unverified`. |
| **F6 (secondary)** | "Disabling a namespace does not force-detach an open AMQP producer link." | **Uncertain.** Plausible and consistent with the observation, but not documented by Microsoft. | Recorded as `observed` with `mechanismConfidence: unverified`, and raised as **CS-5**. |

**Rule adopted from this exercise:** every `fault-semantics.md` entry separates `observedEffect` (what was measured, with citations) from `candidateMechanism` (why we think it happened) and carries a `mechanismConfidence` of `verified` \| `plausible` \| `unverified`. **Only `observedEffect` may drive a verdict.** A behaviour oracle seeded with a misattributed mechanism is worse than an empty one.

## Problem Statement

**P1 — No mid-journey entry.** `start-chaos` (B1) owns a fixed four-phase pipeline and resumes from state; the class-B prototype exposed one skill covering nine steps. Neither lets a user who already has a run ID enter at "diagnose this run", or ask "which scenarios are eligible for this scope" without starting a pipeline. Entering mid-journey degrades to manual mode, and manual mode **loses the invariants** (F14).

**P2 — Fabricated scenario knowledge is a live temptation.** The class-B `scenario-catalog.v1.json` hard-codes eleven scenario families and regex name patterns. `main` is already better here — T5/T6 read the service — but nothing *enforces* that scenario names come only from a service read.

**P3 — Control-plane assertions masquerading as disruption proof.** Chaos reports what it *intended* to mutate. F6 proves intent ≠ effect. Neither `chaos-impact`'s signal classification (B7) nor the prototype distinguishes control-plane mutation from data-plane disruption, so verdicts can be — and were — unsound.

**P4 — Build identity is unprovable.** F1: the prototype gate demanded artifact→deployment→serving-revision proof with no fallback. In practice that is either unsatisfiable (a blocker) or silently skipped (theatre).

**P5 — Telemetry assembly is manual and schema-fragile.** F2 and F4. `monitor_query_logs` (T14) is a raw KQL passthrough and provides no bucketing, no schema normalisation and no subscription injection. `Get-MonitorSignals.ps1` (B6) does much of this — but only inside the PowerShell impact pipeline.

**P6 — Core predicates lack MCP tools.** F3: alert-instance queries required raw `az rest` even though `Constants.ps1` (B10) pins AlertsManagement and `Get-MonitorSignals.ps1` parses alerts. F7: run-ID recovery and per-leg identity are best-effort in `Invoke-RunScenario.ps1` (B4) and absent from `chaos_execute_scenario` (T10).

**P7 — Skills reference tools that may not be available.** F5: three registered tools were absent from the session's tool list. No SKILL.md declares required tools, and there is no preflight or fallback.

**P8 — Non-durable evidence.** F12. On `main`, `Get-StatePath` defaults to a repo-local `startchaos-state.json` (B17); a working-tree wipe destroys the run record, and diagnosis cannot resume after a session ends.

**P9 — Grounding sources inverted.** F9: the prototype `advisory` skill required a matching Advisor recommendation or a named WAF guideline. Advisor will nearly always have no coverage for behaviour-under-fault findings, so the exception clause is the default path — while the genuinely valuable output has no path back into Advisor.

**P10 — Weak no-repeat semantics.** F11: recording attempted *fixes* rather than failure *mechanism classes* let one error class recur three times.

**P11 — Ranking ignores consumer coupling.** F13: a fix scored in isolation ranked last, then became the correctness blocker for a higher-ranked fix that shipped first.

## Goals and Non-Goals

### Goals

- **G1** — Eight independently invocable targeted capabilities, each owning one journey step, each emitting a versioned JSON artifact and next-step guidance — layered onto the five shipped skills, which keep working. No agent handoffs.
- **G2** — Zero hard-coded scenario/fault tables. Scenario, action, capability, eligibility and prerequisite data is read from the service (extending T5/T6 plus the v1 `targetTypes`/`capabilityTypes` catalog) and cached with explicit freshness.
- **G3** — Every recommendation carries evidence with provenance, freshness and a confidence band; no recommendation may cite a scenario the service has not returned for that scope.
- **G4** — Deterministic-by-default: discovery, eligibility joins, scoring, blast-radius computation, window arithmetic, fault-landed proof, work-starvation checks and verdict derivation are computed by code, following the pure-function pattern already proven in `Build-ImpactCorrelation.ps1` (B7). The model produces only semantic analysis, hypotheses and narrative.
- **G5** — Fault-landed proof is **two-sided**: a control-plane attestation (ARM entity state, per F15 — not the Activity Log) *and* a per-leg data-plane disruption attestation. Control-plane-only proof yields `NOT EXERCISED` for that leg.
- **G6** — Build identity is attested through a documented **fallback ladder** with the used rung recorded (F1).
- **G7** — One fault-window pack returns the complete pre/during/post evidence bundle for a run ID, on the correct App Insights schema, including fired alert instances (F2, F3, F4).
- **G8** — Every skill declares its required MCP tools; a preflight reconciliation against the host-visible inventory fails fast, names the missing tools, and offers a documented fallback (F5).
- **G9** — Evidence is persisted durably outside the repository working tree, mirrored after every phase, and re-openable by run ID in a later session — **added beside** the existing `STARTCHAOS_STATE_PATH` contract, not by breaking it (F12, P8).
- **G10** — Verdicts are `CONFIRMED` / `REFUTED` / `NOT EXERCISED` only, computed by a deterministic matrix over numeric evidence.
- **G11** — Chaos Studio product/service defects are tracked separately from skill-instruction changes, with the plan degrading gracefully around each open defect.

### Non-Goals

- **N1** — Not a code-remediation agent. The class-B `coding` phase and autonomous PR authoring are out of scope. Analysis may describe a remediation; it does not implement one.
- **N2** — No new Azure control-plane surface is designed here. Service-side gaps (CS-1…CS-10) are filed, not built.
- **N3** — Not a replacement for `chaos-impact` (B5–B16). Its schema, thresholds, KQL templates, Pester tests and offline replay are retained and extended.
- **N4** — No unattended, approval-free fault injection. Execution always crosses an explicit human approval boundary.
- **N5** — No source-repository write access. Repositories are read-only inputs to analysis.
- **N6** — Not an SLO management product. SLO/SLI definitions are consumed as inputs.
- **N7** — No general Azure inventory tool. Inventory is scoped to what chaos targeting, telemetry correlation and blast-radius computation require.
- **N8** — Advisor is not a grounding gate (F9). Advisor data is optional context and a *destination* for chaos findings.

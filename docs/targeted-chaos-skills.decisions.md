# Azure Chaos Reliability Study — Executive Decision Summary

> **Date:** 2026-08-25 | **Author:** Generated by Octane plan workflow | **Audience:** Engineering leadership, architects, cross-team stakeholders | **Status:** Approved (Technical: 90/100, Readability: 93/100)

## What We're Building

An opinionated **Azure Chaos reliability study** experience built on top of the shipped `startchaos` Copilot CLI plugin. A *study* is one named, dated, reproducible unit of work: pick a scope, state a hypothesis, run a small number of real Chaos Studio faults inside a bounded window, measure against a captured steady-state baseline, and produce a **self-contained HTML report** carrying an executive summary, dated evidence, prioritized findings, mandatory limitations and per-finding remediation. Results are written once, immutably, outside the repository and outside session-temporary state — so a later conversation with no memory of the first can list previous studies, compare two, and rerun one.

The product is built **directly over `az chaos`**. It is not an SRE-Agent feature, it does not require an MCP server, and it is not the never-merged chaos-loop controller. It is also not one monolithic skill: it is **five composable skills** with one obvious entry point and four supporting skills covering discovery/readiness, execution/monitoring, reporting, and comparison/rerun. Every user-facing skill definition stays principle-led under a mechanically enforced 200-line cap, reaching fault-specific detail through progressive discovery into a versioned guidance pack. Every deterministic or safety-critical behaviour — validation gates, consent, blast-radius resolution, window arithmetic, redaction, atomic writes, report rendering — lives in tested PowerShell, never in prompt text.

**Kubernetes is the first complete vertical slice.** Concretely, a user types:

```
chaos-study -Scope <resource-group> -Question "does checkout survive losing a pod?"
```

The suite probes which fault path is actually available, runs a seven-check AKS readiness preflight, forms a falsifiable hypothesis, renders a plan card (fault, resolved blast radius, duration, abort conditions, signals) and **stops** — dry run is the default. On explicit typed consent it freezes and validates the configuration, executes, captures pre/during/post telemetry windows, derives findings, seals the study and emits `report.html`.

- **Deployment model:** a local Copilot CLI plugin. PowerShell 7 only for the core path — no Node, no Python, no browser engine, no network at report time.
- **Data flow:** one direction — Azure control/data plane → deterministic collectors → typed artifacts → sealed study → HTML report. The model narrates; it never writes a number.
- **Auth:** unchanged from the shipped plugin (CLI or managed identity). Least privilege: `Reader` for readiness and history; `Chaos Studio Experiment Contributor` plus AKS Cluster Admin on the cluster for execution.
- **Persistence:** two sibling stores — the existing mutable, run-keyed evidence store (90-day default) and the new immutable, date-keyed study store (365-day default). The study store is built on the evidence store's redaction, canonicalization and atomic-write primitives.
- **Extensibility:** a new fault is a new guidance file plus one routing-table row — no code change.

## Decisions Made

### Product Shape

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Product unit | A dated, sealed, reportable **study** — not a loop or controller | Teams schedule reviews around an artifact, not a state machine |
| Skill count | Five study skills: one opinionated entry + four independently useful supporting skills | One skill can't stay principle-led across readiness, execution, reporting and comparison; users ask those four questions separately |
| Shipped skills | Unchanged in v0.4.x; the five new skills are the marketed workflow | Backward compatibility; the total surface is honestly ten, with one obvious way in |
| Prompt-surface control | Hard sub-200-line cap on every user-facing skill definition, enforced in CI | The largest shipped skill already drifted to 181 lines by accretion; review alone won't hold the line |
| Fault knowledge | A schema-validated guidance pack, one file per fault, reached by progressive discovery | Keeps front doors principle-led and makes new faults additive |
| Division of labour | The model proposes and narrates; scripts compute severities, numbers and limitations | Determinism and safety cannot depend on prompt behaviour |
| First vertical | Kubernetes only in the first release | One complete vertical proves the fault-path split; five shallow ones prove nothing |
| Prior prototype | The chaos-loop pull request is closed and replaced, not extended | Its state machine and repo-local state are the problems being removed; four useful patterns are re-expressed and credited |

### Azure Integration

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Primary control plane | `az chaos` (v2) through the existing single wrapper seam | The wrapper already carries the retry and error contract; no ad-hoc CLI or REST from prompt text |
| Kubernetes reachability | A thin, allowlisted, version-pinned REST wrapper for the classic experiment model | The eight AKS faults are classic-model only and the classic CLI was removed — a capability regression filed with the service team |
| Fault path selection | Discovered at runtime by a capability probe; recorded in the study manifest; never guessed | The v2 catalog has no AKS templates today; hard-coding either path guarantees breakage when that changes |
| API versions | Stay on the shipped preview pin; any bump is evidence-gated, not assumption-driven | A published version proves the version exists, not that the operation is deployed |
| Pin locality | One pin file per language | Prevents literal drift; the existing dead-pin lint test extends to cover it |
| Kubernetes prerequisites | Detect and instruct only — the suite never installs into a customer cluster | Installing from a chaos tool crosses a trust boundary |
| MCP adapter | Optional accelerator; absence selects the script path and records the substitution | Never silently substitute — but never make an accelerator a hard dependency either |

### Evidence and Reporting

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Result durability | Immutable, dated, enumerable study store outside the repo and outside temp state | Temp-directory wipes previously destroyed two runs of evidence |
| Mutation model | Seal once; reruns create a new study that records what it derived from | Mutable results can't be compared or trusted; seal-then-append is also the cheapest correct concurrency model |
| Store construction | Built **on** the existing evidence primitives, not beside them | Forking the hardest-won redaction and atomicity code would double the audit surface |
| Deliverable | A single self-contained HTML file — inline CSS, inline SVG, no CDN, no JS requirement | Reports are emailed, attached to tickets and opened from `file://` on locked-down machines |
| Determinism | Byte-identical output for identical inputs except one generated-at field | Two studies must be diffable, or comparison is worthless |
| Verdict vocabulary | Findings carry severity, confidence and an explicit "was the mechanism proven?" flag | Control-plane state is not disruption proof; the internal three-verdict matrix is retained for derivation but not shown to readers |
| Limitations | Mandatory, non-empty, script-generated | "Here is what we did *not* prove" is the most valuable sentence in a chaos report and the first one dropped if optional |
| Offline history | List, show and compare make **zero** Azure calls; a zipped study is readable on another machine | Historical analysis must survive credential loss and subscription deletion |

### Safety, Security and Compatibility

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Execution consent | Typed human consent bound to a frozen configuration hash; any drift aborts with a diff | Explicit disclosure of every mutation before it happens |
| Broad permission grants | A second, separate, stronger consent; targeted minimum-scope grants always proposed first | Least privilege by default; the broad fix must be a deliberate act |
| Validation gate | The delivered validate → fix → revalidate gate is preserved unchanged | It is correct, tested, and the highest-risk code in the repository |
| Unattended execution | No flag, variable or file grants execution consent to the study skills | One legacy non-interactive escape hatch exists in shipped code and is scheduled for closure |
| Observability failure mode | A missing provider is `unknown`, never `fail`; a plan blocks only if **no** source can evaluate its predicate | Prevents both false blocks and polished-but-empty reports |
| Missing data | `null` plus a caveat; a reported zero must be a measured zero | Null-vs-zero conflation is a contract violation with a dedicated test |
| Secret hygiene | Redaction by key name and value shape, on write and on read, across the study store and the command trail | A planted token must appear nowhere in a sealed study |
| Compatibility | Additive through v0.4.x — skill names, tool signatures, state files and report schema all frozen | Existing users resume without migration; any deprecation gets two minor releases |
| Auditability | Every Azure invocation recorded with command, exit code, duration and version, arguments redacted | A failed study is reproducible from the manifest without replaying the conversation |

## Follow-up Design Items

| Item | Priority | Description |
|------|----------|-------------|
| Consolidate the ten-skill surface | High | Decide at v0.5, with usage data, whether the five shipped low-level skills stay, get aliased into the study suite, or are deprecated over two minor releases |
| Validate that five study skills is the right number | High | Re-evaluate after the first usability round; the leading alternative is folding reporting into execution |
| Close the legacy non-interactive execution escape hatch | High | A shipped skill still honours a non-interactive environment variable; removing it is scheduled release work |
| Adopt the newer preview API version | Medium | Two preview versions are in play with no published difference; bump only once a target environment has exercised the required operations |
| Tighten or relax study comparability rules | Medium | Starting strict — a refused comparison with a stated reason is recoverable, a misleading delta is not |
| Ship a Markdown report format | Medium | HTML first; a secondary Markdown format only if the diff-in-a-pull-request use case is actually requested |
| Reference-layer bloat control | Medium | The guidance-pack schema and an index-bijection test cap fault guides, but the principle documents are capped only by review — a known soft spot |
| Add study-level MCP tools | Low | Deferred until a host actually asks for cross-process study access |
| Reverse-Advisor flow | Low | Chaos-proven findings could be emitted in an Advisor-candidate shape; a partner conversation, not scheduled work |
| Source and infrastructure-as-code analysis | Low | Deferred with a named trigger — revisit only if findings routinely cannot be acted on without code context, and as a new design document |
| Unexplained telemetry query failure | Low | One of three recorded causes was never identified; deliberately left unmitigated rather than guessing at a mechanism |
